# Формулы для бухгалтера

seller_analytics_bot · версия 1.0.21 · схема 21 · 05.10.2026

## 1. Базы расчёта и пропуски

Заказы, финансовые начисления и рекламная атрибуция - разные базы. Результат магазина и экономика товаров являются оперативной оценкой по заказам. Они не заменяют учёт реализованных продаж, расходов предприятия и налогов.

| Показатель | Что означает | Чего не доказывает |
| --- | --- | --- |
| ordered_units | Заказанные товарные единицы | Это не число чеков и не выкупы |
| ordered_revenue | Денежная сумма операционных заказов источника | Не признанная бухгалтерская выручка |
| financial_sales | Продажи финансового источника | Не банковская выплата |
| goods_payable | К перечислению за товар WB | Не окончательный платёж после всех удержаний |
| marketplace_net | Подписанные начисления Ozon | Не чистая прибыль и не поступление в банк |
| bank_payment | Итог к оплате `bankPaymentSum` по финансовому отчёту WB | Удержания и корректировки отчётного периода; не подтверждение банковского перевода |
| ad_attributed_sales | Продажи, приписанные рекламе площадкой | Не дополнительная прибыль от рекламы |

WB: основной агрегат — сумма orderCount и orderSum из «Воронки продаж» по всем карточкам за один московский день. cancelCount показывается отдельно и не вычитается из заказов. Если воронка недоступна и ещё не загружена, резерв — «Статистика», где одна строка заказа считается одной единицей. Источник явно подписан. Статистика также сохраняется для сверки отдельных заказов и схем складов; она может не включать заказы с неподтверждённой оплатой. Ozon: агрегат — ordered_units и revenue Analytics; postings FBO/FBS хранятся отдельно, второй раз не прибавляются. Границы запросов postings — московские календарные дни, переданные в UTC.

Денежные базы WB и Ozon пока не унифицированы: общий денежный результат скрыт, площадки проверять отдельно. В финансовых ответах поддерживается RUB; чужая валюта отклоняется, конвертации нет. SQLite хранит суммы как REAL; финансовый отчёт и нетто Ozon в дневном отчёте выводятся с двумя знаками после запятой. Для проводок нужны первичные документы и политика округления бухгалтера.

Используется последняя успешная/частичная версия метрики за день. Ошибка API не заменяет прежнюю сумму нулём. Частичные и предварительные данные отмечаются, но не становятся подтверждёнными автоматически.

**0** - полученное нулевое значение. **«—»** - неизвестное значение/недостаточная база. Отсутствующая себестоимость не является нулевой. Явно заданная стоимость 0 допустима; её смысл должен подтвердить бухгалтер.

## 2. Периоды и себестоимость

| Расчёт | Формула / условие |
| --- | --- |
| Общее количество | U_total = U_WB + U_Ozon, если все подключённые источники дали данные |
| Доля площадки | U_market / U_total × 100, при полном итоге и U_total > 0 |
| Сумма на единицу | ordered_revenue / ordered_units, при units > 0; не средний чек |
| Изменение периода | (U_current - U_previous) / U_previous × 100, при U_previous > 0 |
| Алерт падения | (Mean_previous - U_yesterday) / Mean_previous × 100, при Mean_previous > 0 |

Если предыдущая база 0, появление спроса не имеет процента роста: показывается переход «с 0». Ноль в обеих базах - без изменений. Алерт сравнивает вчера с предыдущими полными днями, а не с неполным сегодня.

Для периода D дней текущая загруженная дата сравнивается с датой ровно D дней назад. Если доступны 4 позиции из 7, сравниваются те же 4 календарные позиции прошлого периода. Если нужной предыдущей позиции нет, процент не рассчитывается. При переходе WB со «Статистики» на «Воронку продаж» сравнение также скрыто, пока сопоставляемые даты используют разные источники; историю нужно обновить.

**COGS_est = сумма [ordered_units(i,d) × cost_price(i,d)] по товарам и дням.**

Берётся последняя стоимость с effective_date не позже дня заказа. Новая стоимость не меняет прошлые дни автоматически.

**Coverage = covered_ordered_units / expected_ordered_units × 100.**

Знаменатель - агрегатные единицы площадки, а не только товары с загрузившейся детализацией. Проверяется совпадение товарных и агрегатных единиц по каждому дню. Покрытие стоимости 100% не доказывает полноту финансов, рекламы и всех дней периода.

## 3. Управленческий результат и SKU

**R_est = ordered_revenue - COGS_est - E_marketplace - ad_spend + compensation.**

**E_marketplace = commission + logistics + storage + acceptance + acquiring + services + penalties.**

Для Ozon за день с загруженными начислениями services уже включает рекламу. Из E_marketplace выделяется finance_ad_spend, и эта же сумма становится ad_spend: общий расход не меняется и вычитается один раз. Performance за этот день остаётся справочной метрикой для рекламной аналитики. За дни без начислений в операционной оценке используется расход Performance, с предупреждением о предварительной базе. В старых снимках без finance_ad_spend услуги учитываются целиком, а Performance за те же дни не вычитается; обновление /finance добавляет разбивку даже при неизменном ответе API.

Результат рассчитывается только при достаточной базе заказов и полностью покрытой стоимости. При отсутствии стоимости или несовпадении товарных/агрегатных единиц - «—». Явно нулевые единицы и денежная сумма дают COGS_est = 0; известные расходы остаются расходами.

Пример: 100 000 - 40 000 - 10 000 - 5 000 + 1 000 = **46 000 рублей**. Это оценка по заказам до неизвестных расходов, налогов и других затрат. Отмены и возвраты не превращают её в прибыль реализованных товаров. Отсутствующая комиссия/реклама показывается предупреждением: их фактический размер неизвестен.

**SKU_before = SKU_order_revenue - SKU_COGS_est.**

**SKU_after = SKU_before - known_SKU_expenses - SKU_ad_spend + SKU_compensation.**

Показатель SKU требует положительных единиц, денежной базы и покрытой стоимости. Общие расходы магазина не распределяются по SKU без подтверждённой привязки. Сумма результатов SKU поэтому может отличаться от результата магазина.

## 4. Финансовые поля и знаки

В SKU-оценке Ozon применён тот же дневной принцип: Performance вычитается только за дни без загруженных начислений данного подключения. При наличии начислений Performance показан справочно; `finance_ad_spend` товара уже входит в его `services`. Даже старые начисления без отдельной рекламной метрики защищены от повторного вычитания. Общие услуги без товарной привязки не распределяются по SKU; сумма товарных результатов не является полной прибылью магазина.

`/sources` показывает наличие дней и последнюю проверку API по каждому компоненту. Полный набор дней не доказывает окончательность финансового отчёта. `/accruals` использует последний сохранённый успешный ответ Ozon за каждый день и содержит операции, source_run_id и типы удержаний; частично загруженный период явно подписывается. Денежные начисления суммируются через Decimal и округляются до копеек на границе метрики; структура REAL в старой SQLite сохранена.

| Источник | База в коде |
| --- | --- |
| WB список отчётов | Типы одного дня складываются; повтор reportId не учитывается дважды |
| WB продажи / к перечислению / банк | retailAmountSum / forPaySum / bankPaymentSum |
| WB логистика / хранение / приёмка | deliveryServiceSum / paidStorageSum / paidAcceptanceSum |
| WB услуги / штрафы / доплаты | deductionSum / penaltySum / additionalPaymentSum |
| WB товарные суммы | retailAmount, forPay (старое ppvz_for_pay), deliveryService, paidStorage, paidAcceptance, deduction, penalty, additionalPayment |
| Ozon нетто | Сумма total_amount всех начислений дня, со знаком |
| Ozon финансовые продажи | seller_price продуктов категории POSTING; старый ответ без категории допускается |
| Ozon комиссия / логистика | Минус сумма sale_commission / total_accrued |
| Ozon услуги | Минус подписанные accrued из item_fees, non_item_fee, container_fees |
| Ozon реклама по начислениям | Минус подписанные accrued для type_id 41 (клик) и 54 (заказ); это часть services, не дополнительный расход |

WB документ «Возврат» уменьшает продажи и к перечислению: применяется **-abs(amount)**, уже отрицательная сумма не вычитается второй раз. Повторная исправленная строка с тем же rrdId обновляет финансовое событие без дубля. Для известных WB расходов сохраняется действовавшая методика абсолютных значений; её корректировки нужно отдельно сверить с документами.

Ozon: расходы - отрицательные потоки. Комиссия -150 и корректировка +30 дают расход **120**, а не 150/180. Корректировки услуг тоже уменьшают расходы. Количество товара не умножает seller_price без подтверждения методики источника.

**Ограничение WB:** используемый список отчётов не даёт отдельную полную комиссию. ppvzSalesCommission, vw, vwNds, acquiringFee, СПП и cashback не превращаются автоматически в полный расход продавца. НДС, вознаграждение и эквайринг могут пересекаться с выплатой. Управленческая оценка WB может не включать комиссию/приём платежей; предупреждение об этом нужно воспринимать буквально.

Если комиссия уже удержана в выплате, её нельзя вычесть повторно. Бот не подставляет bank_payment или marketplace_net вместо ordered_revenue в R_est. В Ozon повторный вычет Performance поверх финансовых услуг устранён. Нераспознанные виды услуг остаются в services и не пропадают из расходов. Для WB возможные пересечения рекламного и финансового источников требуют отдельной проверки.

## 5. Реклама и сверка этапов

**ДРР = ad_spend / ad_attributed_sales × 100**, только при sales > 0.

**ROAS = ad_attributed_sales / ad_spend**, только при spend > 0.

5 000 рублей рекламы / 25 000 продаж = ДРР **20%**, ROAS **5**. При spend > 0, sales = 0: ROAS = 0, ДРР не определён. Общий ДРР периода считается из сумм, не средним процентов кампаний. Ozon ordersMoney используется и для кампаний, и для общего рекламного показателя. Рекламные продажи не добавляются к общей выручке второй раз.

WB связывает заказ с продажей/финансовой строкой по srid; Ozon posting с финансами по posting_number. Analytics Ozon не даёт posting ID для такого точного сопоставления.

**Gap_WB = max(0, ordered - cancelled) - (sale - return).**

**Gap_Ozon = ordered_units - posting_units.**

**ID coverage = matched_IDs / eligible_IDs × 100**, при ненулевой базе. Gap - расхождение этапов/дат, не доказательство ущерба. При совпадении ID более позднее начисление может участвовать в сверке раннего заказа.

## 6. Остатки и план поставок

Простой отчёт: **V_avg = units за успешно загруженные дни / число этих дней**. Дни до появления товара исключаются, API-пропуск не считается нулём спроса.

**Runway = available_units / V_avg**, при известном остатке и V_avg > 0. Неизвестный спрос и нулевой спрос - разные состояния. Ozon использует present, резерв хранится отдельно; WB - quantity. Доступность резервов для отгрузки требует проверки методики склада.

Для поставок знаменатель - прогнозная скорость F; дни запаса могут отличаться от простого отчёта.

### Спрос по будущим дням

1. Полные дни заказов всех включённых площадок и связанные listings физического товара дают историю. Среднее = Mean.
2. WMA = sum(v_j × j) / sum(j) по последним n ≤ 28 наблюдениям; j = 1…n, новые дни тяжелее.
3. При ≥7 наблюдениях Base = max(0, 0.65 × WMA + 0.35 × Mean), иначе Mean.
4. При достаточной базе прошлый эффект промо удаляется из промодней перед оценкой Base.
5. Bias_factor = clip(1 - 0.5 × Bias_fraction, 0.85, 1.15). Требуются ≥3 завершённых горизонта текущего метода и положительный суммарный факт.
6. F = Base × Bias_factor. Demand_d = F × Weekday_factor_d × Promo_factor_d.

Weekday factor: среднее данного дня недели / общее среднее, первоначально ограничение 0.5…1.5, затем нормирование среднего семи коэффициентов к 1. Нужны ≥28 наблюдений и ≥3 каждого дня недели; иначе 1.

Промо: ≥4 полных промодней и ≥14 обычных. Ratio = clip(mean_promo / mean_normal, 0.80, 1.50). Factor = 1 + (Ratio - 1) × min(0.75, promo_days / 14). Иначе 1. Будущее промо влияет только при подтверждённом участии товара.

### Потребность

L = lead_time_days + learned_lead_buffer; S = safety_stock_days + learned_safety_buffer; T = target_stock_days.

**Reorder = sum(Demand_d за следующие L + S дней).**

**Target = sum(Demand_d за следующие L + S + T дней).**

Учитываются поставки с известной ETA не раньше даты расчёта и не позже соответствующего горизонта. Просроченная неподтверждённая поставка потребность не уменьшает.

Если available + inbound_Reorder ≤ Reorder, остаток известен и F > 0:

**Q_raw = max(0, Target - available - inbound_Target).** Иначе Q_raw = 0.

При Q_raw > 0: **Q = ceil(max(Q_raw, MOQ) / pack_size) × pack_size**.

Низкая достоверность, старая дата остатка и неполная товарная связка требуют проверки менеджером. План не оформляет закупку автоматически и не моделирует потерянный спрос при отсутствии товара.

## 7. ABC/XYZ, качество и буферы

ABC основан на единицах, не прибыли. Товары сортируются по убыванию units. По накопленной доле **до включения текущего товара**: <80% - A, <95% - B, остальные C. При общем нуле - C.

XYZ: полные календарные недели понедельник-воскресенье, минимум 4 недели. **CV = population_stddev(weekly_units) / mean(weekly_units)**. X при CV ≤ 0.25; Y при CV ≤ 0.50; иначе Z. Недостаточно недель - «?»; средний ноль - Z. Пропуски нельзя склеивать в искусственную неделю.

| Метрика качества | Формула |
| --- | --- |
| Абсолютная ошибка | abs(predicted_horizon_units - actual_horizon_units) |
| MAE | Среднее абсолютных ошибок по проверенным горизонтам |
| WAPE | sum(abs(predicted - actual)) / sum(actual) × 100 |
| Bias | (sum(predicted) - sum(actual)) / sum(actual) × 100 |

При sum(actual) = 0 WAPE/Bias не определены. Отдельный нулевой горизонт включается в ошибку и общий bias. WAPE не гасит разнонаправленные ошибки. Положительный bias - завышение, отрицательный - занижение.

Пример: прогнозы 10/10, факты 5/15. WAPE = (5 + 5) / 20 × 100 = **50%**, Bias = **0%**.

Качество проверяется базовой моделью seasonal-wma-v3-backtest; производственный план использует calibrated-promo-bias-wma-v6. Это разные модели. WAPE не подтверждает точность окончательного плана с промо, bias и буферами. Для такого обещания нужен журнал фактически выданных прогнозов и будущего результата.

Safety buffer: при ≥4 образцах WAPE 20/35/60% добавляет 1/2/3 дня; доля нулевых остатков 5/15/30% при ≥7 наблюдениях добавляет 1/2/3 дня. Сумма ограничена настройкой максимума. Lead buffer: ceil(P75 подтверждённых задержек приёмки), при ≥3 образцах, тоже с максимумом. Буферы дополняют настройки продавца.

## 8. Проверка с бухгалтером

- Согласовать состав cost_price, НДС и дату действия стоимости; текущая стоимость относится к заказанным единицам, а не реализованной себестоимости.
- Сверить вознаграждение WB, СПП, приём платежей, НДС и компенсации без двойного вычета.
- Для Ozon сверять рекламу по начислениям со справочным Performance, учитывая разные даты начисления. Для WB отдельно проверить пересечения расходов. Учесть отсутствующие налоги, зарплату, аренду, кредиты, списания и внешнюю рекламу.
- Выбрать завершённую неделю: 3 продажи, 1 возврат, 1 корректировка услуги и 1 товар без стоимости. Сверить общий отчёт, SKU и банковскую выписку.

Источники: код app/services/finance.py, wb_funnel.py, reconciliation.py, supply.py, promotions.py; app/reports/management.py, sku_finance.py, period.py, ads.py; app/storage/repositories.py. Официальная документация WB: https://dev.wildberries.ru/en/openapi/analytics и https://dev.wildberries.ru/docs/openapi/financial-reports-and-accounting . Ozon: https://docs.ozon.ru/api/seller/ . Для сверки нужны исходный отчёт или экран бухгалтера и те же дата, кабинет, фильтры и вид суммы. Операции API и строки XLSX могут группироваться по-разному; сверять следует идентификаторы и подписанные составляющие, а не число строк. Живой ответ воронки WB проверяется после обновления на хостинге клиента.

## Единый ежедневный блок (1.0.20)

- **Заказано**: дата создания заказа, прежние источники WB/Ozon. Общая сумма использует показанные цены; Ozon в иностранной валюте пересчитывается по ЦБ как оценка.
- **WB выкуплено/возвращено**: строки продаж/возвратов по `date` в московском календаре. Один уникальный `saleID` — один товар; `S` — продажа, `R` — возврат. Сумма — `abs(finishedPrice)`, возвраты показываются положительным объёмом отдельно. Нулевую/отсутствующую цену положительного количества источник может ещё заполнять; вместо неё не подставляется `priceWithDisc`.
- **WB отменено**: уникальные `srid` с `isCancel=true`, чей `cancelDate` относится к выбранному дню. `date` заказа и `lastChangeDate` не заменяют дату отмены.
- **Ozon клиентские возвраты**: только `ClientReturn` из `/v1/returns/list` по `logistic.return_date`, сумма `product.quantity`. `FullReturn`, `PartialReturn`, `Cancellation`, `Unknown` не добавляются к возвратам после вручения. Цена возврата берётся из `product.price` лишь при подтверждённых рублях; цена без комиссии её не заменяет.
- **Ozon выкуплено**: `delivery_commission.quantity` из `/v1/finance/realization/by-day`. Это дневная реализация, а не статусы заказов выбранного дня. День задаётся запросом; цены, суммы и валюта проверяются отдельно. В проверенном ответе API доступ ограничен подпиской Premium Plus; отказ отображается явно. Бот запрашивает последние 32 календарных дня.
- **Выкуп товаров самим Ozon**: отдельный `/v1/finance/products/buyout` для товаров с `is_marketplace_buyout=true`. Полные списки FBO/FBS без таких товаров подтверждают отсутствие необходимости в запросе. Неполный список или неизвестный признак этого не подтверждают. HTTP 429 останавливает текущий запрос и последующие окна; сохранённые цены не удаляются. Этот отчёт не заменяет дневную реализацию продаж покупателям.
- **Ozon отменено по дате события**: полный источник пока не подтверждён. Когортные отмены аналитики, даты создания/последнего изменения и движение возврата не подставляются.
- Каждый показатель читается из последнего снимка своего источника. Повторная загрузка не складывается с предыдущей; исправленный пустой ответ заменяет прежний результат. Неполный/неизвестный ответ не становится нулём, неудачный запрос сохраняет прежние значения с предупреждением.
