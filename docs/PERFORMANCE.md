# Производительность SellerBot

Первый этап без удаления истории и изменения расчётов:
- Контекст Database.session закрывает соединение после commit/rollback. Основные методы Repository переведены на него.
- Индекс idx_inventory_scheme_history создаётся при обычном запуске, не переписывает данные и не требует миграции версии схемы. При первом запуске потребуется дополнительное место на диске под индекс.
- Тяжёлые экспортные операции и резервные копии выполняются в отдельном потоке, с общей очередью из одной одновременно работающей операции.
- Проверка SQLite вынесена из event loop. Лимиты API и логика повторов не изменены.
- Техническая команда /health показывает RSS процесса, память и файловый кеш cgroup (когда доступны), CPU за интервал, размеры SQLite/WAL, очередь тяжёлых операций, замеры запросов API и обновления отчётов. Замеры в памяти ограничены последними 64 вызовами каждого внутреннего типа. Значения HTTP 429 в этом экране относятся к итоговому ответу после повторов. Публичный HTTP health не содержит этих данных.

Для проверки: перезапустите бота из актуального main, откройте /tech → состояние бота (/health), сделайте обычный отчёт, полное обновление и экспорт, затем снова /health. Сравнивайте RSS с графиком Bothost (память контейнера может включать файловый кеш). Резервные копии, история и тарифные ограничения сохраняются. Сжатие исторических raw_payloads требует отдельной проверки совместимости и места на диске; существующие строки не удаляются.
