# Яндекс Маркет

Подключение поддерживается общей сборкой и всеми тарифными сборками. Доступ к разделам и расписанию сохраняется по тарифу. Сборщик читает API, не меняет товары, цены, акции и заказы.

## Переменные Bothost

```dotenv
YANDEX_MARKET_API_KEY=
YANDEX_MARKET_BUSINESS_ID=
YANDEX_MARKET_CAMPAIGN_ID=
```

API_KEY — API-Key-токен кабинета Маркета с доступом «Просмотр всех данных» (`all-methods:read-only`). Создайте в кабинете: Настройки → API и модули → Токены авторизации.

BUSINESS_ID — существующий ID кабинета. CAMPAIGN_ID — существующий технический ID магазина (не рекламной кампании). Их не нужно придумывать или создавать: скопируйте из настроек API. API также возвращает их через GET /v2/campaigns. Бот проверяет, что campaignId принадлежит businessId и доступен ключу.

Для другого профиля окружения используйте `SELLERBOT_<ПРОФИЛЬ>_YANDEX_MARKET_API_KEY`, `SELLERBOT_<ПРОФИЛЬ>_YANDEX_MARKET_BUSINESS_ID`, `SELLERBOT_<ПРОФИЛЬ>_YANDEX_MARKET_CAMPAIGN_ID`. Один профиль соответствует одному кабинету Маркета и одному или нескольким его магазинам. Не подключайте один campaignId к нескольким магазинам SellerBot, если собираете общие итоги.

Для трёх магазинов одного кабинета укажите в Bothost одно значение (числа ниже — пример):

```dotenv
YANDEX_MARKET_CAMPAIGN_ID=11111111,22222222,33333333
```

API_KEY и BUSINESS_ID общие. Пробелы вокруг ID разрешены, повторы игнорируются. Пустой элемент, ноль, отрицательное число или чужой магазин отклоняются. Каждый ID берите из раздела API как campaignId, а не из списка складов.

Заказы и услуги суммируются, товары объединяются по SKU внутри кабинета. Общий физический склад учитывается один раз; при несовпадающих остатках обновление отклоняется. Снимок записывается только после успешного получения всех выбранных магазинов. Проблемы карточек содержат ID магазина, успешный статус другого магазина не отменяет проблему. Акции кабинета объединяются без дублей, поставки сохраняют ID магазина. После изменения списка заново загрузите историю нужного периода, чтобы старые дневные показатели также включали все магазины. Для разных кабинетов нужны разные профили.

После обновления кода из main задайте все три значения, перезапустите бота, выберите магазин и нажмите «Проверить API». Затем загрузите историю заказов и обновите остатки. Не публикуйте ключ в GitHub или Telegram. Автоматическая миграция базы сохраняет историю WB/Ozon; штатный безопасный запуск делает резервную копию перед миграцией.

## Что собирается

- Заказы и товарные единицы, сумма оплаты, баллов Плюса и компенсаций скидок Маркета за все оформленные единицы, отдельно — без отмен и отмены среди заказов выбранной даты; история и разбивка по модели работы. Используется новый POST /v1/businesses/{businessId}/orders. Дата заказа — Москва. Сумма позиции уже включает все её единицы и повторно на количество не умножается.
- Доступные и зарезервированные остатки по складам. Для обычных партнёрских складов и групп складов используются разные методы. FIT включает резерв; он не суммируется с AVAILABLE. Остатки участвуют в отчётах и прогнозе запаса.
- Размещение и состояния карточек: отклонение Маркетом, ошибки размещения и создания/изменения карточки. Уведомления используют существующие настройки проверки карточек. Повторы одинакового состояния подавляются, подтверждённое исправление фиксируется. Пустой остаток, архив или неизвестный статус не означают блокировку/исправление.
- Детализация стоимости услуг и буста продаж по заказам, созданным за выбранный период. Буст является частью услуг и не вычитается дважды.
- Акции Маркета и конкретные участвующие SKU. Частичное автоматическое участие фильтруется по campaignId. Акции, созданные самим продавцом, этот метод Маркета не возвращает.
- Заявки на поставку FBY/LaaS и товары в них: план, принятое количество, оставшийся объём и плановая дата. Закрытые заявки и родительские заявки с дочерними не удваивают ожидаемый остаток. Для FBS/DBS/Express этот источник поставок неприменим.

Сбор запускается существующими ежедневными/повторными задачами и командами соответствующего тарифа. Ошибки API сохраняются как ошибки источника; последняя успешная статистика остаётся доступной. Незавершённая пагинация не считается полным ответом. Данные покупателя (адреса и телефоны) из заказов не сохраняются.

## Сумма заказов и сверка с кабинетом

Сумма заказанных товаров = `items[].prices.payment` + `cashback` + `subsidy` (рублёвые значения всей позиции). Не включаются доставка покупателю, комиссии, логистика, реклама и другие расходы продавца. В основных метриках, включая SKU и схемы, учитываются все оформленные единицы, включая отменённые. Отмены среди заказов выбранной даты и сумма без отмен выводятся отдельно; это не отмены по дате события. Для суммы без отмен частичная отмена позиции распределяется пропорционально с округлением до копеек. Это оперативный расчёт; совпадение с кабинетом проверяется на реальных данных. В основном отчёте для всех площадок используется «Заказано». Официальная сводка включает отмены: https://www.yandex.ru/support/marketplace/ru/analytics/overview . Совпадение с конкретным экраном кабинета следует проверять по одинаковым фильтрам и датам.

После обновления повторно загрузите всю нужную историю заказов Яндекс Маркета (в том числе период прогнозирования). Миграция 24 сохраняет старые значения под архивными ключами, исключая их из текущих отчётов и прогнозов до повторной загрузки. WB/Ozon не меняются. Исходные цены заказов не хранятся, поэтому из старой суммы компенсации восстановить нельзя. Успешная повторная загрузка заменяет прежнюю дневную сумму, не прибавляет её повторно. Сравнивайте одинаковые магазины, день по Москве и показатель созданных заказов. Точное совпадение с кабинетом не подтверждено до реальной сверки; возможны различия фильтров, задержки обновления и изменения заказов. Отдельный отчет `ORDER_ITEMS_TOTAL_AMOUNT` пока не подключен: генерация без подписки ограничена одним запросом в 10 минут, поэтому не используется для ежедневной загрузки каждого дня истории.

## Границы данных

Это не полное равенство всех показателей WB/Ozon. Отдельные банковские выплаты, полная рекламная статистика (показы, клики, атрибутированные продажи), выкупы/возвраты/отмены по точной дате события для Маркета пока не реализованы. Они отмечаются как неподтверждённые, не заменяются нулями или суммой заказов. Стоимость услуг в текущем финансовом блоке относится к дате создания заказа, не к дате начисления. Нельзя использовать её как бухгалтерскую прибыль или банковскую выплату.

Автотесты используют контролируемые ответы API. Реальную авторизацию и доступность данных конкретного кабинета нужно проверить после ввода ключа.
