# Как пользоваться ботом

Инструкция и аудит запуска · версия 1.0.2 · схема 15 · 01.10.2026

## Ежедневные 5 минут

1. **Магазин → Список магазинов / Выбрать магазин.** Рабочий магазин - #1 «ИП Карпенко В.В». Не возвращаться к старому дублю «Основной магазин».
2. **Проблемы → Состояние данных.** Проверить свежесть и пропуски. Старые цифры в базе не становятся свежими от открытия отчёта.
3. **Отчёты → Вчера.** Посмотреть заказанные единицы, отмены и сравнение. При «неполных данных» общий итог ещё не подтверждён.
4. **Проблемы → Что делать сегодня.** Открыть задачу. «Принято» отмечает, что её увидели; «Отложить на 24 ч» временно убирает из очереди. Исходную проблему это не исправляет.
5. **Товары → Остатки**, затем **Поставки → План поставок.** Проверить рисковые товары, дату снимка, упаковку и поставки в пути. Закупку согласовать вручную.

## Для чего разделы

| Меню | Польза |
| --- | --- |
| Отчёты | Вчера, неделя, месяц, другая дата и загруженная история. «Месяц» - последние 30 дней, не календарный месяц |
| Товары | Топ, остатки, экономика по товарам, импорт себестоимости |
| Деньги и реклама | Финансы, реклама, результат магазина, проверка расхождений. Обновления финансов и рекламы разделены |
| Поставки | План, поставки в пути, акции и точность базового прогноза |
| Проблемы | Приоритетные действия, активные проблемы, свежесть и история действий |
| Магазин | Выбор, настройки, «Что настроено», «Проверить API», мастер и доступ сотрудников |
| Ещё | Экспорт Excel/CSV ZIP; «Техническое» - состояние бота, ошибки/повторы, backup и обслуживание |

«Назад» возвращает на уровень выше, «Главное меню» открывает разделы, «Отмена» закрывает текущий мастер. Основные сценарии не требуют action_key, SKU или ID вручную. Служебные действия доступны по роли.

Обычные отчёты читают базу. API вызывают явные обновления, загрузка истории, проверка подключений и фоновые циклы. «Месяц» не запускает новый импорт.

## Первый запуск после обновления

1. Выключить демо: синтетические данные не проверяют реальные подключения.
2. **Магазин → Что настроено** проверяет локальную готовность. **Проверить API** делает живые проверки доступа. Ping не подтверждает остатки и полноту финансов.
3. **Отчёты → Догрузить данные**: сначала 7 дней, затем нужная история. Успешно сохранённые дни повторно не скачиваются; ошибки/пропуски видны.
4. При долгом ожидании после 429 нажать **Остановить загрузку**. Сохранённые дни остаются; продолжать после указанного cooldown.
5. **Товары → Импорт себестоимости**: CSV/XLSX. Обязательные поля marketplace, sku, cost_price; полезны effective_date, internal_sku, name. Сначала должны существовать товары после загрузки заказов.
6. **Деньги и реклама → Обновить финансы**, затем отдельно **Обновить рекламу**, если её API подключены. Ozon Performance - отдельные ключи, необязательная функция.
7. Проверить результат и экономику товаров. Неполная стоимость скрывает результат. Незагруженные расходы означают оценку только по известным удержаниям.
8. **Поставки → Обновить поставки в пути**; при необходимости обновить акции. Просроченная неподтверждённая ETA потребность не уменьшает.

### Себестоимость: пример CSV

```text
marketplace;sku;cost_price;effective_date;internal_sku;name
ozon;123456;250;2026-09-01;ITEM-A;Название товара
```

Новая стоимость не применяется к старым заказам до effective_date. Формулы Excel должны быть пересчитаны и сохранены в файле: бот читает готовые значения. Общий физический товар WB/Ozon связывается через internal_sku; разные размеры/модели нельзя объединять по похожему названию.

## Если цифры вызывают сомнение

| Симптом | Что проверить |
| --- | --- |
| Мало дней в периоде | «Что уже загружено», пропуски и догрузку; сравнение использует те же календарные позиции |
| 401/403 | Срок и категории прав ключа на стороне площадки. Повторный запрос права не добавляет |
| 429 / ожидание | Дождаться указанного cooldown; не повторять обновления подряд |
| WB остатки 403 | Известное ограничение endpoints; автоматические повторы подавлены. Ozon продолжает независимо |
| «—» у результата | Стоимость, даты её действия и товарную детализацию |
| Результат слишком большой | Предупреждения комиссии/рекламы; оценка заказов не равна прибыли |
| Странная поставка | Связи SKU, дату остатка, ETA, упаковку, lead/safety/target |

## Bothost: подготовка и проверка

Запуск: Dockerfile / python main.py. Настроить постоянное хранение данных на стороне хостинга: абсолютный путь сам по себе не гарантирует сохранность при redeploy.

Минимальные env: TELEGRAM_BOT_TOKEN, TELEGRAM_OWNER_ID, WB_API_TOKEN и/или OZON_CLIENT_ID + OZON_API_KEY. Для вашей базы: **DB_FILE=/app/data/seller_analytics.sqlite3**. Реклама Ozon при необходимости: OZON_PERF_CLIENT_ID и OZON_PERF_CLIENT_SECRET.

Ключи задавать в закрытых переменных Bothost. Не вставлять в чат, репозиторий, таблицы или скриншоты. WB - один Personal token с чтением и нужными категориями; код не может исправить права API.

До обновления: **Ещё → Техническое → Создать backup**, сохранить копию вне контейнера. Схема 1.0.2 остаётся 15; при переходе с 14 безопасная миграция создаёт страховую копию. Она не заменяет внешнюю копию.

После обновления: startup schema=15, ожидаемый DB_FILE, shops=1 для вашей конфигурации. Если активен лишний дубль, архивировать именно его через меню. Не архивировать #1 и не удалять базу для исправления дублей.

### Проверка без передачи токенов

В консоли контейнера, из /app:

```text
python scripts/preflight.py
python scripts/live_audit.py --shop-id 1 --output /app/data/live_audit_1.json
```

Preflight проверяет env, каталог и схему; может выполнить безопасную миграцию. Live audit читает существующую БД и делает ограниченные запросы: Telegram getMe, кабинет, заказы одной даты, Ozon остатки и страницу финансов более ранней даты. Не изменяет магазины/метрики, не импортирует историю, не отправляет сообщения и не запускает polling. Отчёт не содержит ключей, имён продавцов, SKU, сумм и сырых ответов.

Выходной файл должен быть новым; для повтора выбрать live_audit_2.json. Существующий файл/база/env не перезаписываются. Заблокированные остатки WB проверять только при необходимости с --include-wb-stocks и соблюдением cooldown. У этих двух проверок общий лимит; второй endpoint может потребовать отдельного ожидания.

Коды: 0 - базовые проверки БД/владельца/Telegram/заказов подключённых источников успешны; 1 - не прошли; 2 - ошибка конфигурации/файла. Даже при 0 проверить optional_failures, sample_only, empty, warnings. Одна страница/пустой ответ не подтверждает историю. Реклама, поставки и бухгалтерская сверка этой утилитой не сертифицируются.

### Граница готовности

Код проверяют pytest, compileall, pip check, release_audit и preflight в GitHub CI. Это проверка конкретного commit, а не установки Bothost. Реальные ключи и база хостинга в этой сессии не предоставлены.

Для рабочего допуска проверить: постоянную базу и backup, один экземпляр polling, API именно #1, нужную историю и стоимость, одну завершённую неделю с бухгалтером. Полная прибыль WB и точность окончательного прогноза пока не подтверждены.

Оставить сейчас: ежедневные отчёты, пропуски, себестоимость, проблемы, остатки, экспорт и backup. Сложную калибровку/акции использовать после стабильной базы. Автоставки, изменение цен и закупки отложить. Удалять историю или существующие функции ради упрощения не требуется.

Роли: viewer читает; analyst обновляет и анализирует; owner управляет магазином/доступами. Backup/restore и профили всего экземпляра - только system owner из TELEGRAM_OWNER_ID.
