# Changelog

## 1.0.29 — 2026-10-10

- Снятие предупреждения по запасу не называется восстановлением остатка. Сообщение показывает текущие количества по схемам и прогноз в днях.
- Пропавшая строка ранее использованной схемы и неудачный запрос остатков не подтверждают нормализацию. Старое предупреждение сохраняется; появляется задача «Проверить остатки».
- Явный ноль на ранее использованной FBS/FBO/FBW не перекрывается положительным остатком другой схемы. Переход к нулю оповещает сразу, повторные уведомления соблюдают паузу.
- Некорректный ответ WB без списка items не считается успешным пустым снимком. Исходные успешные отчёты об остатках WB сохраняются для последующей сверки.
- Изменение общего запаса, API-данных и прогноза показано раздельно. Структура БД и переменные запуска не меняются.

## 1.0.28 — 2026-10-08

- Приём Push уведомлений Ozon об отменах FBO и FBS/rFBS, доступный во всех уровнях. HTTP работает в том же процессе, читает порт БотХоста и отдаёт /health и /ready.
- В техническом меню владелец создаёт отдельный защищённый адрес для магазина. Секрет выдаётся в личном чате, в БД хранится только хеш. Замена требует подтверждения и отключает старый адрес; прежние отмены сохраняются.
- Исходные JSON сохраняются в БД. Штуки — сумма products.quantity; день — cancel_date для FBO или changed_state_date для FBS, по Москве. TYPE_ORDER_CANCELLED без состава товаров не добавляет штуки.
- Повторы не удваивают итог. Конфликтующие версии исключаются и сохраняются для проверки. Seller ID отправителя закрепляется первым корректным событием. Другой отправитель отклоняется; смена кабинета требует нового адреса. Старые адреса не обходят ограничения уровня на магазины.
- Дневной отчёт показывает подтверждённую часть «≥ N шт. · по уведомлениям». Отсутствие уведомлений не считается нулём. Исторические и пропущенные события автоматически не восстанавливаются; сумма отмен не выводится из цены заказа.
- Схема 22. Обновление проверено на копии настоящего бэкапа: прежние записи и целостность сохранены. Инструкция: docs/OZON_PUSH_RU.md.

## 1.0.27 — 2026-10-08

- Реклама Ozon по товарам получает ID всех кампаний за период, в том числе остановленных. Запросы SKU отправляются партиями; пустой список не уходит в API.
- Сохраняются исходные рекламные ответы и сведения о запросах без OAuth-секретов. Ошибка разбора сохраняет ответ для диагностики и прежние успешные данные.
- Поддержано поле расходов moneySpent. Отсутствующие, пустые и некорректные денежные поля не превращаются в ноль. Подтверждённый ноль и полный пустой ответ обрабатываются отдельно.
- Исторические расходы Ozon без исходного ответа отмечены как неподтверждённые в рекламе, выгрузке и управленческой оценке. Начисленная реклама из финансовых источников сохраняет свою отдельную базу.
- Повторная загрузка не удваивает расходы. Полный новый снимок заменяет прежние значения, включая старые записи другого рекламного источника; сбой партии SKU сохраняет прежний полный снимок.
- Оперативный метод SKU ограничен сегодняшним и предыдущим днём. Более старые данные берутся из сохранённого архива с пояснением; расходы по кампаниям загружаются за выбранный период. Ограничение истории не запускает бесконечные повторные попытки.
- Ошибки фоновой рекламы показывают конкретную причину вместо advertising retry remains partial. Схема БД остаётся 21, новые переменные не нужны.

- Обычные отчёты и сотрудники сохраняют права по конкретному магазину. Длинный архив перелистывается; доступ к страницам проверяется при каждом нажатии. Схема БД остаётся 21. Инструкция: `docs/UPDATE_1_0_26_RU.md`.

## 1.0.24 — 2026-10-06

- Ручные, автоматические и страховочные резервные копии сохраняются в ZIP на сервере. Архив сверяется с исходной базой по SHA-256; только после проверки удаляется исходная SQLite-копия. При ошибке сжатия проверенная база сохраняется. Telegram отправляет готовый архив без повторного сжатия.
- По умолчанию хранятся копии за 7 дней, до 10 файлов и до 512 МиБ. Последняя исправная копия и файлы во время отправки/восстановления защищены; дневные автоматические копии имеют приоритет перед дубликатами. Основная база и посторонние файлы не входят в очистку.
- При запуске и каждый час старые копии, включая pre-migration, переводятся в ZIP после проверки целостности и контрольных сумм; существующая история получает новый путь, размер и SHA-256 архива. Обслуживание хранения не зависит от AUTO_BACKUP_ENABLED и тарифа.
- «История backup» показывает количество и размер копий, правила хранения и пометку удалённых файлов. Восстановление совместимо с прежними SQLite и ZIP; проверен откат из сжатой страховочной копии. Схема БД остаётся 21. Инструкция: `docs/UPDATE_1_0_24_RU.md`.

## 1.0.23 — 2026-10-06

- Разделены продажи покупателям по дневной реализации и отдельный выкуп товаров самим Ozon. Если полные списки FBO/FBS не содержат товаров с `is_marketplace_buyout=true`, отдельный отчёт не запрашивается; его старые ошибки не выводятся для такого дня. При неполных списках отсутствие выкупа не считается доказанным.
- HTTP 429 отдельного отчёта больше не объясняется отсутствием прав API. Запрос останавливается после первого 429, учитывает серверный интервал повторной попытки и не блокирует обычные начисления. Последующие финансовые окна в той же загрузке не запрашиваются; сохранённые цены остаются доступными.
- Отказ Ozon с требованием Premium Plus показывается прямо в ежедневной карточке. Ручная кнопка «Обновить» и обновление всех отчётов повторно проверяют доступ без перезапуска; при повторном отказе выполняется один запрос за период, исходная причина сохраняется.
- Неизвестные отмены обозначены «дата отмены не получена». Подписка и отсутствующая дата не подменяются нулями, статусами заказов или начислениями. Общий баннер сохранённых данных не приписывается показателю, который ещё ни разу не загрузился.
- Схема остаётся 21. Сверка на резервной копии за 05.10.2026 выполнена только для чтения: заказы, цены покупателя, клиентские возвраты и начисления сохранены. Инструкция: `docs/UPDATE_1_0_23_RU.md`.

## 1.0.22 — 2026-10-06

- Ручной backup разделяет создание копии и доставку: ошибка отправки в Telegram больше не сообщает, что копия не создана. В сообщении указаны точный путь и размер сохранённого SQLite-файла.
- Ручные и автоматические копии больше 20 МБ сжимаются во временный ZIP. Проверенный оригинал остаётся в каталоге backups. Если сжатие не помогает или Telegram отклоняет размер, владелец получает путь к оригиналу; автоматическая рассылка не повторяет такой отказ бесконечно.
- Сжатие и создание копии не блокируют цикл событий. Временные ZIP удаляются после доставки; отмена ожидает окончания дисковой работы перед очисткой.
- Восстановление принимает SQLite и ZIP с одним файлом базы, проверяет целостность ZIP и SQLite, запрещает вложенные пути и лишние файлы, ограничивает распакованный размер 200 МиБ. Лимит загрузки через cloud Bot API исправлен на 20 МБ; более крупные доставленные копии явно требуют восстановления через сервер.
- Страховочная копия и атомарная замена базы сохранены. Обновлены справка и памятки; схема БД остаётся 21.

Смена даты редактирует то же сообщение, читает сохранённые данные и сохраняет новую дату для последующего обновления. «Подробнее / Свернуть» и страницы длинных блоков сохранены. Магазин карточки и текущие права проверяются при каждом действии.
